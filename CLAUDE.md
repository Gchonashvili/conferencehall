## What this is

Conferencehall: a conference-hall aggregator for Georgia. Hotels and venues list halls; organizations search, send one booking request, get a confirmation from the venue, and (eventually) pay a deposit online. Product brief: `PRD.md`. Design/market research: `research/`. Full plan history: `/Users/macbook/.claude/plans/mighty-forging-liskov.md`.

Stack: Next.js 16 (App Router) · TypeScript · Tailwind v4 · next-intl (`/ka`, `/en`) · Drizzle ORM + Postgres (Neon in production, PGlite in dev/test) · Better Auth · Mailgun · n8n (WhatsApp) · Railway.

**This is not the Next.js you know.** Next 16 has breaking changes from what most training data reflects — e.g. `middleware.ts` is now `proxy.ts`, and `params`/`searchParams` are async. ### The local database is single-writer — read this before running any DB command

Development and tests use **PGlite** (real Postgres compiled to WASM, running in-process) at `.data/pglite`, unless `DATABASE_URL` is set. Only one process may have it open at a time; a second writer corrupts it. `src/db/local-lock.ts` enforces this with a lock file and a clear error, but you still need to:

- **Stop the dev server before running `pnpm admin ...`, `pnpm db:seed*`, or tests that touch the real dev DB.** Tests use their own fresh in-memory PGlite instance (`createMemoryDb()`), so `pnpm test` is safe to run concurrently with `pnpm dev`.
- **When stopping the dev server, kill both processes**: `next dev` and its child `next-server` (the one that actually opens the database). `pkill -f next-server; pkill -f "next dev"` covers both. Killing only the wrapper leaves the lock held.
- If the local DB ever gets corrupted (`Aborted()` errors from PGlite), delete `.data/pglite` and re-seed.
- Never open the database (`getDb()`) or build the auth instance (`getAuth()`) at module import time — both are lazy singletons for exactly this reason: Next also loads server modules in short-lived worker processes, and eager init there fights the real server for the lock.

## Architecture

### Internationalization is load-bearing, not cosmetic

Every route lives under `src/app/[locale]/...` (`ka` default, `en` also supported; `src/i18n/routing.ts`). `src/proxy.ts` (Next 16's replacement for middleware) handles locale detection/redirects. Pages must validate the locale segment via `resolveLocale()` (`src/i18n/locale.ts`) before rendering. UI strings live in `src/messages/{ka,en}.json` — both files must have identical key sets (enforced by `src/messages/messages.test.ts`). Domain text stored in the DB (hall names, city names, etc.) is bilingual JSON (`{ ka, en }`, typed as `I18n` in `src/db/schema.ts`) and resolved per-request with `pickText()` (`src/lib/i18n-text.ts`), not through next-intl.

### Design tokens are the single source of truth for the visual system

All colors/shape tokens are defined once in `src/app/globals.css` (Tailwind v4 `@theme`), sampled from reference mockups in `research/`. `src/lib/design-tokens.ts` reads them back out of the CSS file at runtime (not duplicated in JS) so `src/lib/contrast.test.ts` can assert WCAG AA contrast against the *actual* deployed values, and so `/[locale]/design` (dev-only design-system review page, 404s in production) can render live swatches. Don't hardcode hex colors elsewhere — reference the CSS custom properties / Tailwind classes.

### Data layer: one lazy `Database` handle, Drizzle schema, transactional outbox

- `src/db/schema.ts` is the single Drizzle schema (business tables + Better Auth's own tables re-exported from `src/db/auth-schema.ts`). Run `pnpm db:generate` after editing it; migrations land in `drizzle/`.
- `getDb()` (`src/db/index.ts`) returns a memoized `Promise<Database>` — Neon/`pg` when `DATABASE_URL` is set, otherwise PGlite. Never construct a client yourself.
- Money is **always** integer tetri (1 GEL = 100 tetri) — see `src/lib/money.ts` for conversion/formatting/parsing. Never use floats for money.
- Dates: `event_date` etc. are plain `date` strings (a calendar day in Georgia), not timestamps. All display formatting goes through `Asia/Tbilisi` (`src/lib/dates.ts`, `src/lib/format-date.ts`). Business logic that needs "now" takes an injected `now: Date` parameter rather than calling `new Date()` directly, so tests are deterministic — follow this pattern in new domain code.
- **Notifications never go out synchronously inside a request that could fail.** `src/lib/outbox.ts` implements a transactional outbox: domain services (`src/domain/booking-service.ts`, `src/domain/inquiry-service.ts`) write the business row *and* queue notification rows in the same DB transaction (`enqueueNotifications`), keyed by a `dedupeKey` so retries can't double-send. `processOutbox()` claims due rows with `FOR UPDATE SKIP LOCKED`, delivers them (`src/lib/notifications/deliver.ts` → Mailgun or a signed n8n webhook), and reschedules failures with exponential backoff (capped, eventually marked `dead`). This is triggered two ways: a best-effort immediate drain after the response (`src/lib/drain.ts`, via `next/server`'s `after()`), and a cron endpoint (`POST /api/cron/outbox`, bearer-token protected, meant to run every minute) as the reliable fallback. When adding a new kind of notification, add a template to `src/lib/notifications/templates.ts` and enqueue it from inside the same transaction as the state change that causes it.
- Bookings follow an explicit state machine (`src/domain/booking.ts`: `pending → accepted/declined/expired → paid → completed`, plus `cancelled`) — always transition through `assertTransition`/`canTransition`, never set `status` directly.

### Auth and access control

Better Auth (`src/lib/auth.ts`, lazily constructed via `getAuth()`) with email/password, required email verification, and three roles: `organizer` (default), `venue`, `admin`. Roles are granted server-side only (`pnpm admin ...`) — the signup form cannot set `role`. `src/lib/session.ts`'s `requireUser(locale, roles?)` is the guard for protected pages/Server Actions; it redirects rather than throwing. **Every Server Action re-checks authorization itself** (e.g. `answerRequest` in `src/app/actions/dashboard.ts` re-verifies the request belongs to the calling venue's own venue) — proxy-level checks are not sufficient since Server Actions are reachable directly by POST. Query functions in `src/db/queries/requests.ts` (`listVenueRequests`, `getVenueRequest`, `listOrganizerRequests`) enforce row-level scoping (a venue only ever sees requests for halls it owns; an organizer's unverified email never grants access to another person's requests by email match) — see the isolation tests in `requests.test.ts` for the exact guarantees.

### Forms: Server Actions, not client-side fetch

Forms in `src/app/actions/*.ts` use React's `useActionState` + Server Actions returning a typed `FormState` (`src/lib/form-state.ts`: `idle | success | error` with per-field `fieldErrors` and echoed `values` so a validation error doesn't wipe what the user typed). Every public form has a honeypot field (`src/components/ui/honeypot.tsx`) and optional Cloudflare Turnstile (`src/lib/turnstile.ts`, no-ops when unconfigured) checked server-side before validation. Validation schemas live next to the domain logic they serve (`src/domain/booking-input.ts`, inline in `inquiry-service.ts`) using Zod, returning stable error *codes* (not prose) that the UI translates via `src/lib/use-error-text.ts` + the `errors` message namespace.

### Stock photography vs. hall photography — a hard boundary

`src/lib/stock-photos.ts` manages a small, license-tracked set of Unsplash "atmosphere" photos (hero, banner, city/event-type tiles). These must **never** be used for anything hall-specific (hall cards, galleries, hall pages) — the product's premise is verified real photos of real rooms. This is enforced by a guardrail test (`src/lib/stock-photos.test.ts`) that greps hall-related source files for any reference to the stock-photo module. If you touch hall-rendering code, don't import `StockImage`/`stock-photos`. New photos are added via `pnpm photos:prepare` (see `research/photo-shortlist.md` for the current shortlist/process) — downloads are manual (Unsplash blocks scripted access) and dropped in `stock-originals/`.

### Environment config

All env vars are validated centrally in `src/env.ts` (Zod). Optional integrations (Mailgun, n8n, Turnstile) degrade to a logged no-op in development when unset, but the same code path throws in production rather than silently dropping messages — don't add a new integration without following that pattern. See `.env.example` for the full list and `README.md` for which vars are required in production and how the Railway deploy (web / cron / n8n services) is wired.
